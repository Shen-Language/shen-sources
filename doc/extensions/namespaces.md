# Experimental namespaces

This extension groups definitions under a name and resolves references before
macro expansion. It requires the kernel's [source-form hooks](../source-forms.md).

Load and initialise it before reading source files that use it:

```shen
(load "extensions/namespaces.shen")
(shen.x.namespaces.initialise)
(load "my-source.shen")
```

Ports can instead load `klambda/extension-namespaces.kl` and call the same
initialiser.

```shen
(shen.x.namespace example.model
  (define make-value X -> X))

(shen.x.namespace example.client
  (use example.model => model)
  (externals [get-value ready])

  (define get-value X -> (model.make-value X))
  (define status -> ready))
```

Here `model.make-value` resolves to `example.model.make-value`. `status` becomes
`example.client.status`, while `get-value` is a global function and `ready`
remains unchanged.

Place these directives before the body:

- `(use Owner)` preserves references beginning with `Owner.`.
- `(use Owner => Alias)` replaces the `Alias.` prefix with `Owner.`.
- `(externals Expression)` leaves the resulting symbols unchanged throughout
  the namespace, including definition names.
- `(export Name ...)` publishes names; see [Exports and imports](#exports-and-imports).
- `(import Owner Name ...)` lets the body use another namespace's names bare.
- `(shadow Name ...)` makes system names local to the namespace; see
  [Shadowing system names](#shadowing-system-names).

As with `package`, the `externals` expression is evaluated once before
qualification, in the surrounding environment. It must return a proper list of
non-variable symbols. Literal lists still work; ordinary functions can share and
combine vocabularies:

```shen
(externals (append (example.syntax.vocabulary) [get-value ready]))
```

Load vocabulary definitions before reading the namespace. Its `use` aliases do
not apply to the expression, and definitions in its body are not yet available.

References work in calls and data, including names generated by macros.
Undeclared dotted prefixes remain local. The most specific declared prefix
wins when prefixes overlap; an exact external symbol takes precedence.

## Exports and imports

A namespace with an `export` directive publishes only the names it lists.
`From => To` publishes a name under another one.

```shen
(shen.x.namespace example.shape
  (export make area side => width)

  (define make S -> [square S])
  (define side [square S] -> S)
  (define area Shape -> (* (side Shape) (side Shape)))
  (define helper -> unused))

(shen.x.namespace example.drawing
  (use example.shape => shape)
  (import example.shape make area => size)

  (define f X -> (size (make X)))
  (define g X -> (shape.width (make X))))
```

`import` binds bare names in the body, renamed with `=>` or not: `size` here is
`example.shape.area`. A reference through a `use` prefix must name a published
name too, so `shape.width` is `example.shape.side`, while `shape.helper` and
`shape.side` fail when the file is read. A namespace without exports remains
open, as does an owner not read yet, or a package: its members are qualified
without a check. Read owners first to have references checked.

The name on the left of `=>` resolves as the body's names do, so a namespace can
re-export another's names, and those stand for the original definitions:

```shen
(shen.x.namespace example.graphics
  (use example.shape => shape)
  (export shape.make => square shape.area => area))
```

A re-export through a `use` prefix needs a name of its own, as the prefix means
nothing to other namespaces. An exported external stays unchanged when
imported, so a namespace can publish a macro's vocabulary with
`(externals [mov return])` and `(export mov return)`.

Blocks of one namespace add to its exports, and a published name stands for one
symbol only. Reading a namespace again keeps its exports. A local name can be
imported once, cannot also be an external, and cannot be defined by the
namespace's own `define`, `defmacro`, `defprolog`, `defcc` or `datatype`.
Scoped externals take precedence over imports, as they do over aliases.

Exports concern names only. Datatype rules stay global, so exporting a type's
name lets other code state rules about it, as `declare` can for any type.

## Shadowing system names

System functions keep their names inside a namespace, so `(define length ...)`
would redefine the kernel's. `shadow` makes names the namespace's own in that
block, wherever they appear:

```shen
(shen.x.namespace example.lists
  (shadow length)
  (export length)

  (define length L -> (count L 0))
  (define count [] N -> N
                [_ | L] N -> (count L (+ N 1))))
```

Elsewhere `length` is still the kernel's. Other namespaces can write
`lists.length` after `(use example.lists => lists)`, or import it.

A datatype label that is a system name would stay global, and a second namespace
using it would replace the first one's rules. Reading such a datatype fails
unless its label is shadowed, imported or external.

## Syntax annotation hooks

A DSL can preserve literal syntax without making its whole vocabulary external.
Register its annotator before reading consumers:

```shen
(define example.annotate-field
  [example.field Label Expression]
  -> [example.field [protect Label] Expression])

(shen.x.namespaces.register-syntax
  example.field (fn example.annotate-field))
```

Namespaces resolves a form's head first, including `use` prefixes, imports and
shadowing. A registered annotator receives that canonical head and the original,
unqualified arguments. It returns one proper form with the same head, adding
`protect` around literal syntax. Namespaces then qualifies the arguments in the
caller's scope. It does not resolve the returned head again. Unregistered forms
keep their ordinary behavior; this does not change macro expansion order.

For example, `(field size (size X))`, with `field` imported from `example`,
keeps its first `size` literal while resolving the function call normally.
Protection may enclose an entire field descriptor or other compound syntax.
`(protect X)` survives this pass intact, so later free-variable checking can
still honor it. A DSL expander should unwrap protection only in the literal
positions it consumes, leaving expression arguments alone. System punctuation
such as `<-` and `;` already stays unchanged and needs no wrapper.

`(shen.x.namespaces.unregister-syntax Head)` removes an annotator. Registration
and removal return `Head`; registering again replaces the previous handler.
Heads must be non-variable symbols. Handler errors propagate; returning a
changed head or an improper form raises. Registrations survive another call to
`initialise` and are ordinary image state.

A declaration which generates definitions can separately register a name
enumerator with `(shen.x.namespaces.register-definitions Head Names)`. Like an
annotator, `Names` receives the resolved head and raw arguments. It returns a
proper list of the literal names the declaration introduces, in their original
spelling. These names are checked against imports before qualification, so a
generated accessor cannot silently conflict with an imported alias. This hook
does not expand the declaration or register its schema. Remove it with
`(shen.x.namespaces.unregister-definitions Head)`; registration and removal
return `Head`. Both hooks are registered once per declaration syntax, rather
than once per declared type.

## Scoped externals

Within a namespace, `with-externals` adds names for one enclosed form. Its first
argument is evaluated by the same rules as `externals`. For example, with an
assembly macro already loaded:

```shen
(define assemble X ->
  (with-externals [asm mov return]
    (asm
      (mov Result (model.make-value X))
      (return Result))))
```

The wrapper disappears before macro expansion. Other names still resolve
normally, including `model.make-value`. Nested scopes inherit outer externals;
the added names stop applying outside the enclosed form.

Preservation applies to every occurrence of a listed symbol within that form.
To call a local function with the same name, use its qualified name, such as
`example.client.mov`.

Load dependencies explicitly. Multiple files can contribute to the same
namespace through top-level blocks.
